# Python ↔ Rust/WASM consistency

The NumPy package is the readable reference implementation. `web-core` ports
the same v1 equations to dependency-light Rust and exposes them through
`wasm-bindgen` for the browser worker. Both implementations use:

- `f64` state and the same Choi–Okos lean-meat mixture;
- the same analytic roast, ham, slab, and bird SDFs;
- 3×3×3 volume and 3×3 face quadrature;
- the same 0.25 effective cut-cell volume floor;
- harmonic shared-face conduction and embedded surface area construction;
- lagged convection, exact lagged T⁴ radiation, finite per-cell moisture,
  synthetic wet-surface closure, pan insulation, rest, and pasteurization
  integration; and
- the same conservative discrete energy ledger.

`fixtures/rust_golden.tsv` is generated by
`python/scripts/generate_rust_golden.py`. It contains properties, geometry
summaries, a 120-step full-physics trajectory, moisture, and energy terms.
`web-core/tests/golden.rs` verifies the native Rust core against those values
and smoke-tests every preset and rest mode. The fixture is deterministic and
**synthetic**; it is neither experimental data nor an empirical calibration.

The production browser build uses the same Rust crate. `web/worker.js` owns the
WASM object, advances it in short simulated-time chunks, yields between chunks,
and streams summary/slice messages. This gives progressive execution without
blocking rendering. M7/WebGPU is intentionally not present.

## Regenerating and checking

From the repository development environment:

```sh
PYTHONPATH=python python python/scripts/generate_rust_golden.py
cargo test --manifest-path web-core/Cargo.toml
wasm-pack build web-core --target web --out-dir ../web/wasm --release
```

Golden tolerances are deliberately tight because both CPU implementations are
`f64` ports, but the test checks practical aggregate/trajectory outputs rather
than requiring a bit-identical field. A fixture change should be reviewed as a
physics change, not blindly accepted.
