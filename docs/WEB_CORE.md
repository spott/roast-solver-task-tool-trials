# Rust/WASM core

`web-core` is a dependency-light Rust port of the reference kernel. It uses the
same Choi–Okos coefficients, preset equations and scaling constants, Float32
temperature field, harmonic interior links, normal-corrected embedded area,
Robin distance resistance, radiation, local moisture stages, pan mask,
lagged properties, rest boundary, and P70 integral as Python.

The release WASM target enables `simd128` in `web-core/.cargo/config.toml`; LLVM
may vectorize suitable loops. There is no WebGPU path (M7 is out of scope).

## Regression policy

`fixtures/python_golden.json` is generated by `scripts/generate_fixtures.py`.
`web-core/tests/golden.rs` checks:

- 20 °C properties to tight floating-point tolerance;
- grid dimensions, volume, and corrected area for roast and slab;
- 30-minute coldest, stable-probe, and hottest temperatures within 0.08 °C;
- progressive roast/rest phase completion and energy accounting.

This is a practical regression lock rather than a claim of bit identity across
NumPy, native Rust, and browser WASM. Any intentional physics change should be
made in both implementations, analytically revalidated, and then regenerate the
synthetic oracle.

## Worker protocol

`web/src/solver.worker.ts` owns the WASM instance. A `start` message carries the
JSON `Config`; `cancel` invalidates the current generation. The worker advances
24 stable explicit steps, posts a JSON snapshot (`started`, `progress`, then
`complete`), and yields with a zero-duration timer. The main thread never runs
the solver and remains interactive. Snapshots contain curves, phase/progress,
pull/carryover values, P70, energy error, and a nullable middle temperature
slice.

Build glue and optimized WASM with `scripts/build-wasm.sh`. The checked-in
`web/src/wasm` output allows ordinary static frontend tooling to resolve the
module, while production builds regenerate it from `Cargo.lock`.
